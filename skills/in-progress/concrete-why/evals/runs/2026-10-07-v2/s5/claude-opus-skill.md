**Short answer:** The HUD doesn't use `GrantedTagRemoval` at all. That value goes back to whichever code removed the tag. The HUD finds out about tag changes another way: a server publisher checks whether a version counter has moved. The project chose this over subscribing on purpose, in [ADR 0003 "A Mutation Returns Its Change"](docs/adr/0003-a-mutation-returns-its-change.md), and a lint rule enforces it. Subscribing would save only a few lines here, and it would bring back problems that this container would actually hit.

**What `GrantedTagRemoval` is for.** `RemoveGrantedTag` (`GameplayTagContainer.ts:266`) tells the caller one of two things. `Removed` means the tag came off and includes the tag's new presence. `NotActive` means this grant was already gone, either because it was handed back twice or because a blocker or a cleanse removed it first. Only the code that removed the tag can use that answer. [ADR 0008](docs/adr/0008-a-cause-is-a-context-not-a-key.md) gives an example: an effect that ticks puts a fresh copy of a tag on every tick, and removing the third copy must not touch the second. A subscriber only hears that the tag changed. It can't tell whether the grant it held was the one removed.

**How the HUD actually updates.** Every apply, removal or stack change adds one to `tagVersion` (`GameplayTagContainer.ts:243, 287, 340`). `ParticipantResourceBarsPublisher.PublishParticipantEffects` (`ParticipantResourceBars.Server.ts:71-75`) compares that number with the last one it sent. If it has moved, it republishes the participant to the party UI. That is the HUD's entire tag wiring: one comparison. Switching to a subscription would replace it with a callback list. It would not remove any wiring.

**If we subscribed like Unreal's `OnGameplayTagAdded`:**
- **Callbacks would run while the container is half-updated.** `ApplyGameplayTag` removes tags in the middle of its own work: granting a blocker removes whatever it blocks, and joining an exclusion group pushes the old member out (`:230-231` → `:678`, `:721`). Say a listener for "burning removed" runs during a fire-immunity grant and applies a tag of its own. That nested apply would run against a list the outer call is still changing. Today nothing runs until the outer call returns.
- **A tag granted at spawn could be missed.** If spawn setup grants `Stunned` before the bar subscribes, the bar never greys out, and it only happens when spawn order shifts. Unreal code avoids this by reading the current tags right after subscribing. That fix works, but every subscriber has to remember to do it.
- **A deleted subscriber still compiles.** The listener map's type doesn't say who reacts to a stun. If someone deletes the bar's subscription, nothing fails until a player notices.
- **It's banned twice over.** The `nro-codestyle/ban-a-list-of-callers-to-tell-later` rule refuses it, and the project's CLAUDE.md lists "dynamic listener lists" as forbidden.

**What the current design costs, honestly.** ADR 0003 assumes one owner applies tags and calls each interested reader directly. The code doesn't match that. The container is passed straight to `EffectGrantsAuthority`, `GameplayAbilitySetAuthority`, `EffectTagHolds` and others. Most callers throw the removal result away. `TagExclusionGroupMembership.ts:98-104` checks it, but both outcomes just `break`. The HUD gets its updates by checking the version counter, not from the returned change. So right now the returned value protects removers from removing the wrong grant, and it isn't yet the channel that delivers changes to readers. Subscribing wouldn't fix that gap, though. It would just remove the ordering guarantee as well.

**What decides it:** apply and remove call each other during a single mutation. That makes code that runs during a mutation unsafe in this container, even though Unreal tolerates it.
