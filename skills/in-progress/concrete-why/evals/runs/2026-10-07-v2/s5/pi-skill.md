<what-to-do>
**Short answer:** Keep the returned `GrantedTagRemoval`. A subscription cannot answer the question the caller actually has at the line where it removes its grant ("was my grant the one lifted, and did the tag leave entirely?"), it double-fires under client prediction replay, and it loses changes to mount ordering — so it is *more* wiring, not less. This exact comparison against Unreal-style tag delegates was decided in [docs/adr/0003-a-mutation-returns-its-change.md](docs/adr/0003-a-mutation-returns-its-change.md), the accepted decision record "A Mutation Returns Its Change", and nothing since has moved the facts it rests on.

**What `RemoveGrantedTag` handing back `GrantedTagRemoval` gains**

`RemoveGrantedTag` is a method on `src/Shared/ReplicatedStorage/GameplayTags/GameplayTagContainer.ts`, the tag container both machines simulate through; `GrantedTagRemoval` (in `GameplayTags/AppliedTag.Types.ts`) is its result: `Removed` carrying the grant and the tag's presence afterwards, or `NotActive/AlreadyRemoved`. Callers depend on both answers:
- One tag can be held by several causes at once — the container keeps an `Applications` list per tag, and blockers, cleanses and exclusion push-outs all call `RemoveGrantedTag` internally (lines 577, 591, 678, 721). So when `EffectTagHolds.ts` or `TagExclusionGroupMembership.ts` hands a grant back, "something about this tag changed" is not what they need to know; they need to know whether *their seat* was removed and whether the tag is now gone or still held by another cause. `GameplayCause.integration.ts:462` pins this: handing back a grant that something else already lifted returns `NotActive` and touches nothing. A "tag count changed" broadcast cannot say either thing to the remover — it would either stay silent (no presence change) or fire per seat and make the HUD diff counts to guess.
- Not reading the result is a build failure — `perfect-typescripter/unconsumed-outcome` refuses a dropped outcome. Not registering a subscriber is silent. The ADR's concrete miss: spawn setup grants `Stunned`, the health bar subscribes one frame later, the bar never greys out, and it reproduces only when spawn ordering shifts.

**What subscribing costs**

- *Removals fire inside grants.* `ApplyGameplayTag` in `GameplayTagContainer.ts` calls `removeTagsBlockedBy`/`removeTagsExcludedBy` (lines 225–226) while the granting call is still on the stack, and those call `RemoveGrantedTag` before `ApplyGameplayTag` logs `ApplicationTaken` or returns. A listener woken there reads a half-updated table and can mutate it back — the ADR's example: granting fire immunity fires "burning removed" listeners in the middle of the immunity grant, and a listener that grants something recurses into the container mid-update. The returned value instead makes the order a readable line: mutate, log, then tell collaborators (ADR 0003's own sample).
- *The client re-runs tag mutations on every server correction.* `src/Shared/Client/Participant/PredictedFacts.Client.ts` rebuilds the participant's containers to the agreed state and re-lands every unconfirmed guess (`rebuildAndReplay`, lines 347–357). A listener cannot tell a replay from a first arrival, so HUD reactions fire twice or fire for a guess the correction retracts. A HUD that reads current state after the rebuild is correct — but then it needs no listener, only to know *when* to re-read.
- *The wiring grows, not shrinks.* Subscribing means a listener list on the container, a connection handle per HUD mount with disposal when the React tree (`UserInterface.Client.tsx`) unmounts, and the startup-ordering contract above. Today's HUD path is one constructor parameter plus one comparison per step: `src/Shared/Server/Participant/ParticipantResourceBars.Server.ts` publishes when `Tags.ReadTagVersion()` moves past `publishedTagVersion` (lines 71–79). A HUD that mounts after the change still shows it, because reads answer "right now" — the missed-window bug is structurally impossible. Writing a subscriber list is also refused at save time by the compiled rule `nro-codestyle/ban-a-list-of-callers-to-tell-later` (`tools/nro-codestyle-rules/`), which names the three failures above as its reason.
- *Honest cost of this side:* every mutation bumps `tagVersion`, so that publisher re-publishes when an unrelated tag flickers even if its own fact did not change, and each owner's constructor carries the collaborators interested in its changes — the ADR concedes this list grows with the game and names its extraction point ("everything which reacts to this change" becomes a thing worth naming) when it stops being readable. That is a per-step version compare and a longer constructor; the subscription side costs missed states and double-fired reactions the player sees.

**What decides it:** the meaning of a change — whose grant it was, why it lifted, what remains — exists only at the call site that made it, so anything reacting to *meaning* must receive the returned value; anything that can be correct by re-reading current state at any moment (a HUD redrawing) is served by the version counter and is broken by listeners in both directions. A listener is the one shape that does neither.
</what-to-do>
