Subscriptions are deliberately banned in NRO. Unreal has them; NRO chose not to, and wrote down why in [ADR 0003, "A mutation returns its change"](docs/adr/0003-a-mutation-returns-its-change.md). It cites Unreal's `OnExactGameplayTagAdded` by name and rejects it for four reasons:

1. **A listener that registers late misses the change, silently.** The ADR's example: a fighter spawns, spawn setup grants `Stunned`, and the health bar subscribes in its own init one frame later. The bar never greys out, and only when spawn order shifts. A return value can't arrive before anyone is there to receive it.
2. **You can delete a reaction and the build still passes.** With a `Map<TagID, Array<callback>>`, nothing in the types says who reacts to a stun, so removing the subscriber still compiles. A returned `GrantedTagRemoval` has to be used: `perfect-typescripter/unconsumed-outcome` fails the build if a caller drops it. A missed reaction becomes a compile error, not a runtime bug that happens once on someone else's machine.
3. **Listeners would run while the container is half-updated.** One tag change triggers others. Granting a blocker strips what it blocks (`removeTagsBlockedBy`, `GameplayTagContainer.ts:659`), and an exclusive tag pushes out the rest of its group (`removeTagsExcludedBy`, `:688`). Both call `RemoveGrantedTag` while `ApplyGameplayTag` is still running. With subscribers, granting fire immunity would fire "burning removed" listeners mid-grant, and one of them could grant another tag and recurse into a half-built table.
4. **The change becomes a value you can work with.** `{ Kind: "Removed", Grant, Presence }` or `{ Kind: "NotActive", Reason: "AlreadyRemoved" }` can be logged, compared against what you expected, batched or dropped. With a subscription, the listeners use it up before control comes back to the caller.

The tooling enforces this too. The `nro-codestyle` rule `ban-a-list-of-callers-to-tell-later` (now in `tools/nro-codestyle-rules/`) rejects the listener-list shape, and the project `CLAUDE.md` forbids event buses and dynamic listener lists.

**On "way less wiring":** the ADR treats that wiring as the point. One owner performs the change and calls the collaborators it was given in its constructor. Adding a reader means adding one constructor parameter in one place, which grows the same way a subscription would but is type-checked and has no startup gap. Roblox's own signals are exempt, and a message system is allowed if the caller passes the returned change into it on a line you can read.

**What the HUD actually does today:** it doesn't consume the removal result directly. The tag container keeps a counter that goes up on every add, removal or stack change (`ReadTagVersion`, `GameplayTagContainer.ts:123`). The effects code calls `ParticipantResourceBarsPublisher.PublishParticipantEffects()` directly after its changes. That method compares the counter with the last one it sent and re-sends the bars if anything changed (`ParticipantResourceBars.Server.ts:65`). So the HUD is called directly, never registered as a listener.

**Why it's a grant and not "remove tag X":** that part comes from [ADR 0008, "A cause is a context, not a key"](docs/adr/0008-a-cause-is-a-context-not-a-key.md). Whoever applies a tag gets back the grant that lifts it, and only that grant lifts it. Two stuns from the same source are two grants that each come off on their own. That is how a repeating stun keeps someone down while each application runs out in turn (header of `GameplayTagContainer.ts`). Removing by tag or by cause would need a lookup and would have to handle "that cause wasn't applying it" or "it was applying it twice." The grant handle makes both of those impossible.

One small thing: ADR 0003's References section still points at `plugins/nro-codestyle/rules/ban-a-list-of-callers-to-tell-later.rule.mjs`, which no longer exists. The rule now lives under `tools/nro-codestyle-rules/`.
