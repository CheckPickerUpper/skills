Based on Architectural Decision Record 0038 (`docs/adr/0038-an-empty-resource-bar-is-a-gameplay-tag.md`), NRO represents an empty resource bar as a gameplay tag rather than directly checking if stamina is 0 inside an ability for several architectural reasons:

1. **Everything already speaks tags:** The game's ability system relies heavily on tags. Phase transitions (`onTagAdded`), activation gates, effect conditions (`runsWhileTagged`), and visual gameplay cues all already know how to read and react to tags. By treating "empty stamina" as a tag, all of these subsystems can instantly react to exhaustion out-of-the-box without needing to invent and duplicate custom `onAttributeEmpty` logic for each of them.
2. **Polling is forbidden:** If Hora's flurry simply checked `if stamina == 0` inside its tick loop, it would be polling state. The project rules forbid polling state to infer facts, as it can cause timing bugs if the check runs in between updates.
3. **A single source of truth:** The attribute container is the only thing that changes the stamina number. By having that container automatically apply the Empty Tag at the exact moment the bar reaches its lower limit, there is only one owner. This guarantees the tag and the actual attribute amount can never disagree.
4. **Out-of-the-box network prediction:** The game predicts gameplay facts using shared code on both the client and server (ADR 0012). Because tags are already predicted over the network, making "empty stamina" a tag means the client can predict the flurry cancellation using the exact same pipeline the server uses to confirm it. 

While writing an `if stamina == 0` check inside Hora's flurry might feel locally simpler for that one ability, using an empty tag allows the entire rest of the game (UI, cancellation logic, and visual cues) to react to exhaustion without writing that same check everywhere.
